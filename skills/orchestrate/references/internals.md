# How an orchestrate job works inside

Reference for the parent when a user asks how something works, or when a job behaves unexpectedly. The single source of truth for numbers is the code (`orchestrate.py --help`, `router.py --help`, and the constants at the top of each script); this file explains the shape.

## Who does what

| Role | Who | Does |
|---|---|---|
| **Parent** | the conversation that loaded the orchestrate skill | grills the user, triages, plans, launches, relays the manager's questions, reports |
| **Manager** | one persistent Opus session per job | supervises every subagent: diagnoses failures, retries with better instructions, splits tasks that are too big, turns open issues and review findings into targeted tasks, asks the user when a decision is needed |
| **Subagents** | `claude -p` workers in their own worktrees | do one task each, on the model routing picks |
| **Integrator / reviewers** | fresh sessions | resolve merge conflicts; review the merged result (per area plus an integration reviewer when the diff is large) |
| **UI reviewer** | fresh session, Read/Grep/Glob only | views the screenshots of the running app and reports what is broken on screen |
| `orchestrate.py` | script | capacity caps, worktrees, briefs, merging, file claims, rule-based triage, and validating and applying the manager's actions |

## Orca mode

`scripts/orca_mode.py`. The parent agent is the Orca coordinator; the script is called once per event and never waits:

- `run` (or `resume`): `prepare_job` (setup, baseline, the manager's pending answer, the advisor's plan check), an Orca Run (`run-create`), then `pump`.
- `pump`: settle queued manager events synchronously, start a worker for each ready task up to the parallel cap (`worker-start --spec-file <brief> --worktree new-child|new-top-level --base-branch orchestrate/<job> --model <id> --effort <e>`), and return exit 10 while workers run. When nothing runs and every task is done, `review_round` runs; if the manager queues nothing for blocking findings, they become a `review-fix-<n>` task that depends on every other task and runs as a worker too.
- `worker-done`: the checks run_task.py runs, on the worker's worktree: scope (with claims), verify, the report at `.orchestrate/report.json` (kept out of git by `info/exclude`), and every done id. Pass: route ledger, `commit_and_merge`, `worker-release`, `worktree rm --delete-branch`, raised criteria, open-issue triage. Fail: the first failure at a model goes back to the same worker with `send`; the second is classified, and the ladder picks the next model, started in the same worktree with a note that a weaker attempt left changes. Out of escalations, or an environment cause: the task fails, its worker stays open, and the manager gets the event.
- `worker-lost`: a worker that stopped without `worker_done` counts as a failed attempt; it is replaced in the same worktree.
- One step at a time per job (`.orca-step.lock`); the skill-files fingerprint is retaken on start and resume and checked at every `worker-done`.

## The manager

It is woken only when judgment is needed:
- **a task fails**, after routing has already escalated models
- **a finished subagent reports `open_issues`** that no rule settles: `fyi` issues are just listed, and `needs_file` issues whose files belong to one not-started task amend that task directly
- **the reviewer requests changes**
- **the user answers its question**

It decides in a background thread. The scheduler keeps launching tasks the decision can't affect, and events that arrive meanwhile reach it as one `batch`. It replies (as schema-checked structured output) with actions: `retry`, `split`, `add_task`, `amend`, `skip`, `fix_round`, `accept`, `ask_human` or `abort`. The script validates them as one batch (ownership, the dependency graph, verify not weakened, migrations gated, limits) and applies all or none. A reply that can't be parsed is re-asked once, then turned into a question for the user. Defaults: at most 12 interventions per job and 2 manager retries per task. Every decision is listed in `report.md`. The user's answer to its question becomes a plan decision before the manager sees it: `record_answer` appends `<question, cut to 200 chars> -> <answer> (decided by the user during job <id>)` to `plan.decisions` in the job's `plan.json` and to `job.state["decisions_added"]` (never twice), so later briefs, the reviewers and the final advisor hold the work to it, and `report.md` lists it under "Decided during the job". `"manager": {"enabled": false}` falls back to plain stop-on-failure and one generic fix round.

Subagent-written text (reports, open issues, log tails, the diff) reaches the manager, reviewer, advisor and integrator only inside `<untrusted source="..." id="...">` tags. The opening and closing tags carry the same random id, generated per block, so text inside can't close the fence early. Prose is sanitized and size-capped; code and diffs keep `<<<` and `>>>` as written, and bidi control characters are shown as `[U+202E]` instead of being dropped.

## The parallelism cap

`capacity` takes the minimum of:
- **memory:** available RAM, including cgroup/container limits, × 0.8 ÷ `mem_per_agent_gb` (default 1.5)
- **CPU:** free CPUs (cores − 1-minute load) ÷ `cpu_per_agent` (default 1)
- **hard max:** 6, for API rate limits
- `plan.max_parallel`, if set

It re-checks free memory before every launch. For heavy monorepos (tsc, Go and Gradle builds in verify), set `"mem_per_agent_gb": 2.5` or more in the plan. Check the numbers with `orchestrate.py capacity`.

## What each subagent receives

A brief in two parts. The first part is identical for every task of the job, so parallel subagents share a cached prompt prefix: the rules, the report format, acceptance, decisions, non-goals, and the repo's root glossary and AGENTS.md inlined when small. The second part is the task: its goal, the paths it **owns**, what to **read first**, what its **upstream tasks** did, notes from the manager, and **done looks like** (its `done` criteria plus `verify` commands).

Its verify steps start with a scope check. A change to a path another task owns, a hotspot or a migration fails the attempt and is fed back. A change to a file that **no task owns** is granted to the task instead, recorded in `claims.json` and added to its `owns`. The report is structured output with typed `open_issues`.

## Review

After every task has merged: the job's final verify, then a reviewer with a fresh context. When the diff exceeds `review_diff_chars`, one reviewer per area runs in parallel and an integration reviewer judges acceptance and cross-area wiring from their verdicts. Every acceptance criterion needs evidence (`file:line` or a test); a criterion that is unassessed, unmet or unevidenced becomes a blocker. A reviewer whose reply isn't the verdict object is re-asked once in the same session (area reviewers too, on the main thread after the parallel calls; not when the budget ran out). A reviewer that still returns no verdict ends the job as `review_failed`, never `done`. Every area blocker or major finding is added to the integration verdict, even when the integration reviewer seems to repeat it: a word match can't tell "the delete endpoint skips the owner check" from "the update endpoint skips the owner check". A likely repeat (same file, at least 60% of its issue words in that finding, `covering_finding`) is tagged `possible_duplicate_of` so the fix round can treat the two as one.

**Stale docs.** `stale_doc_refs` takes the files the job deleted or renamed away (`git diff -M --name-status`), runs `git grep -F` for each path over tracked `*.md` files, skips docs the job itself changed, and keeps at most 20 lines. Paths only: symbol names depend on the language and match too much. The single reviewer, or the integration reviewer for a big diff, gets them in a `<stale_doc_refs>` block (check 8). The round keeps them (`stale_doc_refs`) and `report.md` lists them. Cleanup may only edit the job's own files, so a stale doc becomes a small fix task that owns it.

**Merge conflicts.** The integrator subagent resolves them in the integration worktree. It can't run git, so the harness stages its edits, but only when it replied `resolved: true` and no `<<<<<<<`, `|||||||` or `>>>>>>>` line is left. Only content conflicts (both sides changed the file) go to it: a delete/modify or rename conflict has no markers to judge, so it fails the task for the manager. A merge git refuses without a conflict fails at once, with no integrator call. A crash or interrupt anywhere in the resolution aborts the merge, and the final verify, fix rounds and cleanup clear any merge left open before they start. Before the merge commit, `resolution_verify` runs the merging task's `verify`, then the `verify` of each finished task that owns a conflicted file (no duplicates; first failure stops). A failure, or an interrupt during that verify, aborts the merge and resets what the merge or its verify left in tracked files (when they were clean before), and every merge first clears a merge left open, so a rejected resolution is never concluded by the next one. The integration head doesn't move, and the task fails with `integrator resolution fails verify: <cmd>` and the output tail (also in `tasks.<id>.merge_verify`). Without this, later tasks would start from a broken head with no baseline and take the blame.

**report.md** opens with a "Checks skipped or overridden (not run)" list when there is one: an advisor plan check the user overrode or that was skipped on a resumed job, a final check overridden with `--approve advisor:final` (per round), a job baseline skipped with `--skip-baseline` (`job.state["baseline_skipped"]`), and gated tasks the user approved. So a skipped check never reads as a passed one. Skipped UI reviews are in the UI section.

Reviewers and the advisor report every finding with a `severity` and a `confidence`, and the harness decides what blocks (`blocking_findings`): blocker or major, unless the model marked it low confidence. The model's own `verdict` is kept as `model_verdict`, but the findings set the verdict. This follows Anthropic's code-review harness guidance: a reviewer told to be selective finds bugs and then leaves them out. An unhandled edge case the reviewer didn't list as a finding is added at the severity it gave the case. Judgment schemas put the evidence fields first and the verdict last, because structured output is generated in field order. Reviewer and advisor prompts put the material first (diff, reports, verify output, each fenced), then the playbook and the definition of done, then the task.

## UI review

**Preflight.** In `prepare_job`, after setup and the baseline and before any model call, `ui_review.preflight` starts `ui.dev` once in the integration worktree (under the dev-server lock, port check included) and waits for `ui.url`, then stops it and puts the worktree back. Then `check_chrome` starts Chrome, opens `about:blank` and takes one PNG screenshot. A busy port, a dev command that never answers, or a Chrome that can't take that screenshot (`plan.ui: Chrome can't take screenshots here: ...`) ends the job as `environment`. It runs once per job (`job.state["ui_preflight_ok"]`).

Each round, inside `verify_and_review`, only when the plan has a `ui` block and the final verify passed. Headless and Orca mode both reach it through `review_round`. The capture (no tokens) runs first, then the code review, then the UI reviewer:

1. **Skip check.** With `ui.paths` set, no file of the job's diff (`git_paths`: `--no-renames`, so a file moved away counts by its old path too, and `core.quotePath=off -z`, so a non-ASCII name is matched as itself) matching them (`owned()`-style patterns) and no done task that declared `ui` pages, the round records `skipped: "diff touches no ui.paths"` and nothing runs. `validate` warns when `ui.paths` overlaps no task's `owns`.
2. **Dev server.** Take the lock `router.DIR/devserver.lock` (`fcntl`; one dev server per state dir at a time). Reap what a SIGKILLed run left (`devserver.pids` next to the lock: pid plus `ps -o lstart` start time, so a reused pid is never hit; Chrome's temp profile is removed too). `remove_profile` also deletes the `/tmp/com.google.Chrome.*` scratch dir that Chrome links from the profile's `SingletonSocket` and leaves behind even on a normal close, but only a real directory owned by this user, directly in the temp dir, with a Chrome-style name. If anything accepts a TCP connection on `ui.url`'s host and port (every resolved address), fail: the shots would show other code. Snapshot the worktree (`git status --porcelain -z --untracked-files=all`, with the hash and bytes of each already-changed file). Start `ui.dev` in the integration worktree in its own process group, output to `jobs/<job>/logs/_devserver.log`, and poll `ui.url` (https with an unverified context) until it answers or `ui.ready_timeout_s` (180) passes; then the process group must still be alive. The group is killed afterwards on every path the process survives: normal exit, an exception, SIGTERM or SIGHUP (`signals_raise` turns them into `SystemExit` while the capture runs, so `finally` runs). Then the worktree is put back to the snapshot: tracked files the server changed or deleted are checked out, new untracked files removed, already-changed files get their bytes back (`ui["restored"]`); ignored files are left.
3. **Shots.** Headless Chrome over the DevTools protocol (stdlib only), with `--ignore-certificate-errors` and `--remote-debugging-pipe` (CDP over fds 3 and 4; no debugging port). Pages are the union of `ui.pages` and every task's `ui`, or `/` when there are none; each records the tasks that declared it. Per page and viewport (`desktop` 1440×900; `mobile` 390×844, DPR 2, touch, mobile user agent): load, run the steps (`click`, `type`, `press`, `wait_for` with a 10 s timeout, `wait_ms`, `screenshot`), and save `<integration wt>/.orchestrate/screenshots/round-<n>/<page>--<viewport>[--<step>].png`. A failing step is recorded in `step_errors`, the remaining steps are skipped (`steps N-M were not run`) and the page's final shot is taken. `wait_for`, `click` and `type` need a visible element (a box, and not `display:none`, `visibility:hidden` or opacity 0). A click also fails when the element is off-screen or another element covers its centre; the error names what covers it. Page and screenshot names are a-z0-9 words joined by single dashes, at most 41 chars, so no name holds the `--` that separates the parts of a shot id. A shot's `status` is the status of the main frame's latest document, the one on screen; when the first document's status differs it is kept as `first_status`. JavaScript dialogs are answered at once from the CDP read loop (`Page.handleJavaScriptDialog`, accept) and recorded in `console` as `[dialog <type>] <message>`. A page taller than 1.5 viewports also gets viewport-sized tiles under `round-<n>/tiles/` (`tiles`). A mobile page laid out wider than the viewport (no viewport meta) is captured whole, scaled to the viewport width as a phone shows it, with a line in `notes`. A page whose renderer stops answering (a CDP timeout while the browser itself is alive) gets no shot: it goes to `page_failures` with the step it was on, the tab is closed, and the capture goes on. The dev process group is checked before each page and at the end; if it died, the capture fails (`UIUnavailable`). `.orchestrate/.gitignore` holds `*`, so nothing there reaches git status, scope checks or commits.
4. **UI reviewer** (`models.ROLES["ui_reviewer"]`, Opus 5.5 at medium; prompt starts with `ORCHESTRATE_UI_REVIEW`; tools Read, Grep, Glob; cwd the integration worktree). The prompt lists every shot's file, tiles, page, viewport, step, tasks, HTTP status and console, page, request and step errors and notes, plus the definition of done, acceptance, decisions, non-goals and diff stat. The browser evidence is budgeted per shot (`ui_evidence_json`): every shot keeps its status, step errors, uncaught exceptions, failed requests and notes (repeats folded, at most 8 each); console messages fill the rest of its share, errors before warnings, and the prompt says how many were left out. `<earlier_findings>` lists the last reviewed round's blocking `[UI]` findings (`earlier_ui_findings`, ids `E1`...) with this round's shot of the same page and viewport. Output schema `schemas.UI_REVIEW`: `pages` (one per shot), `findings` (`FINDING`), `expected` (shot, kind `http_4xx`/`step_error`/`page_error`, why), `earlier` (id, observations, fixed), `summary`, `verdict`. A shot with no `pages` entry gets one more turn in the same session (`ORCHESTRATE_UI_REVIEW (missing screenshots)`, naming them); still missing fails closed. After a re-ask both replies count (`merge_ui_replies`): every finding (`_union_findings` drops repeats with the same severity, issue and file), every `expected` entry, and per shot the worse judgement with both observations; `settle_verdict` sets the verdict from them. A page not marked `ok: true` adds a major finding unless one of the reviewer's blocking findings names that shot (`enforce_ui_pages`). An earlier finding with no `earlier` answer, or answered not fixed, is added again at its old severity (`earlier_ui_answers`). Cost goes to `record_call(job, "ui_reviewer", ...)`.
5. **Evidence findings** (`ui_evidence_findings`): status `None` or >= 500 and every `page_failures` entry are blockers; a 4xx document, a step error or an uncaught exception is major unless the reviewer's `expected` lists that shot and kind with a reason (then a minor note with the reason). A finding that only names the shot waives nothing. `_names_shot` matches an id only as a whole token (the full id may end a path such as `.../round-1/x--desktop.png`), so a finding on `x--desktop--step` or `share-view--desktop` doesn't cover `x--desktop` or `view--desktop`.
6. **Merge.** The findings join the round's findings with `[UI] ` prepended to `issue`, and each gets `screenshots` (absolute paths of the shots it names) and `browser_evidence`, so `blocking_findings`, the manager and the fix brief see them. `[UI]` findings are not turned into "Fixed and covered by a test" job criteria: the next round's UI review checks them. `ui_report_lines` prints, per round, the UI reviewer's verdict and the round's UI outcome after the evidence findings, the pages judged wrong, the earlier findings' answers, and each shot's `notes` (a page cut at 4000 CSS px says so).

**Cleanup.** `cleanup_pass` leaves out the files the screenshots depend on (`cleanup_ui_files`: those under `ui.paths` and those owned by a task with `ui` pages; every changed file when `ui.paths` is unset), and reverts a cleanup that edits one anyway, so nothing ships that the UI reviewer did not see.

**Fail closed.** Chrome missing is checked in `prepare_job` before any model call (the job ends `environment`). Chrome lookup: `$ORCHESTRATE_CHROME` when set (nothing else is tried), else `google-chrome-stable`, `google-chrome`, `chromium`, `chromium-browser` on PATH, then the macOS app. At review time, a missing browser, a dev server not ready in time or dead during the capture, a port already taken, a browser crash, reviewer output that can't be parsed, or a screenshot left unassessed makes the round a `reviewer_error` (`review_failed`), never a pass. When the capture itself can't run, the code review is skipped too (no tokens). A dev command that exits before `ui.url` answers (`AppFailed`) is not a reviewer error: after the preflight it is the job's bug, a blocker finding `[UI] the app does not start any more` for the manager and the fix round. Rounds that end in `reviewer_error` don't count toward `review_rounds` (`reviewed_rounds`).

**Fix round.** The fix subagent's task opens with `fix_round_context`: the definition of done, the decisions (answers given during the job included) and the non-goals, then the findings. When it commits nothing, the job ends `review_failed` with the findings, instead of a fresh review of the same code. `legacy_fix_round` never commits a path outside the union of the tasks' `owns` and `review_may_edit`: such paths are put back and listed in the round's `fix.not_committed`.

**State.** `job.state["screenshots_root"]` is the absolute screenshots dir. `clean` moves it to `jobs/<job>/screenshots` with `move_screenshots`, which merges round folders into what an earlier `clean` kept instead of replacing it, and updates the root and each round's `dir`. When a resumed job captures again and the root isn't the integration worktree's, `ui_capture_step` first moves the kept rounds back there, so every round stays under one root. Each `job.state["review"]["rounds"][i]["ui"]` holds `ran`, `skipped`, `error`, `app_failed`, `url`, `dir`, `verdict` (the UI reviewer's output or null), `unreviewed`, `page_failures` (`{name, path, viewport, step, tasks, error}`), `restored`, and `shots`: `{id, name, path, viewport, step, file, status, first_status (only when it differs), title, console, page_errors, failed_requests, step_errors, notes, tiles, tasks}`, with `id` like `round-1/home--desktop` and `file` (and `tiles`) relative to `screenshots_root`.

**Logs.** `log()` writes every progress line to stderr and, once a job runs (`start_job`, `worker-done`, `worker-lost`), to `jobs/<job>/logs/_orchestrator.log` too, in both modes. In Orca mode `task_log` writes what the harness did for a task (worker started, check results with their output, merge, give-up) to `logs/<tid>.log`.

## Dashboard

`scripts/dashboard.py`, stdlib `http.server` on 127.0.0.1 (default port 8765), read-only over `router.DIR/jobs`. `orchestrate.py dashboard [JOB] [--port 8765] [--no-start | --stop]` and every `run`/`resume` (headless, `--detach` and Orca, after the plan validates and before `prepare_job`; not for a finished job) call `ensure_dashboard`. Under `fcntl` lock `router.DIR/dashboard.lock` (concurrent callers share one dashboard), it pings every port from `--port` to +20 and reuses a dashboard serving the same jobs dir, unless that one runs other `dashboard.py` code: a `fingerprint` in its ping that differs from the sha256 of this `dashboard.py`, or a record in `router.DIR/dashboard.json` (0600; pid, port, fingerprint of each dashboard this tool started) whose pid and port match the ping and whose fingerprint differs. A stale dashboard this tool started is SIGTERMed and restarted on the same port; one it did not start is left alone. Otherwise it starts `dashboard.py --port <p>` detached on the first free port (`start_new_session`, output to `router.DIR/dashboard.log`), waits up to 5 s for the ping, and records it. The job id in the URL is URL-encoded. The URL is logged on stderr as `dashboard: <url>`, returned as `dashboard` in `--detach`'s JSON, and stored in `job.state["dashboard"]`. `--stop` SIGTERMs a dashboard of this jobs dir in the range (and the recorded ones) only when its pid is recorded for that port in dashboard.json or `/proc/<pid>/cmdline` runs this `dashboard.py` (never pid <= 1); any other is named on stderr and `--stop` exits 1. The restart path uses the same check. `dashboard.py` exits after `ORCHESTRATE_DASHBOARD_IDLE_HOURS` (or `--idle-hours`; default 12, 0 = never) with no request and no running job in its jobs dir: a job counts as running while its process is alive, or, in Orca mode, while it is `running` and its job.json changed within that window. An open page polls, so it keeps the dashboard up. `ORCHESTRATE_DASHBOARD=0` turns starting it off (the test suites set it).

| Endpoint | Returns |
|---|---|
| `GET /` | the page; for a job that doesn't exist yet it shows the plan from `plans/<id>.json` when that file exists ("planned"), else "waiting for job <id> to start", and keeps polling |
| `GET /api/ping` | `{"orchestrate_dashboard": 1, "jobs_dir": "<abs>", "pid": <int>, "fingerprint": "<first 16 hex of sha256 of the dashboard.py it runs>"}`. `ensure_dashboard` compares `fingerprint` with this `dashboard.py`'s; an open page checks it every 5 s and reloads itself (keeping `?job=` and the hash) when it differs from the code that served the page |
| `GET /api/jobs` | the job list |
| `GET /api/job/<jid>` | the full payload, including `ui_rounds`, `calls`, `screenshots_root`, `dashboard`, `plan_raw` (404 for an unknown job; ETag, 304 when unchanged) |
| `GET /api/job/<jid>/log/<name>?n=` | tail of a task log, `_orchestrator`, `_integration` or `_devserver` (`?n=all` for the whole file) |
| `GET /api/job/<jid>/brief/<tid>` | the task's brief |
| `GET /api/job/<jid>/out` | the detached run's output (`jobs/<jid>.out`) |
| `GET /api/job/<jid>/report` | `report.md` |
| `GET /api/job/<jid>/state` | `job.json` as written |
| `GET /api/job/<jid>/shot?f=<rel>` | a PNG; `f` must resolve (realpath) inside `screenshots_root` and end in `.png`, else 404 |
| `GET /api/job/<jid>/file?path=<rel>` | text of a file in the integration worktree, only one a review finding or a task's merged files name (never `.git`, realpath inside the worktree), else 404 |

Text tails carry `X-Log-Size` and `X-Log-Start`, so the page can say what it isn't showing. A dashboard bound to loopback answers only loopback `Host` names (a DNS-rebinding guard; anything else gets 403). To reach it through a proxy that keeps the browser's `Host` (tailscale serve, SSH, nginx), allow the name with `dashboard.py --allow-host NAME` (repeatable) or `ORCHESTRATE_DASHBOARD_HOSTS=name1,name2`, which dashboards that `orchestrate.py` starts inherit; a name starting with `.` allows its subdomains.

`scan` adds `ui_suggestion` when it finds a web app (a `package.json` with a `dev` script and next, vite, react, vue, svelte, astro, remix or nuxt in its dependencies): `{"dev": "<pm> run dev", "url": "http://localhost:<port>", "paths": ["<pkg dir>/**"]}`. The port is a `--port`/`-p` in the dev script, else the framework's default (Astro 4321; Next, Nuxt, CRA and classic Remix 3000; Vite and the rest 5173). For a package below the root, `dev` targets it (`pnpm --filter <name>`, `npm --prefix <dir>`, `yarn`/`bun --cwd <dir>`) and `paths` is set; packages under `apps/` win. The parent starts the plan's `ui` block from it.

## Routing and escalation (inside every task)

Type is `<category>:<area>`: categories `rename docs config bugfix feature refactor test migration review research`; area is the package's area from `scan`, or `cross`.

Every task starts at the worker role (Opus 5.5 at medium) on the ladder `haiku/low → haiku/medium → sonnet/medium → sonnet/high → opus/low → opus/medium → opus/high → opus/xhigh → fable/high`, whatever its tier; the tier sets how many done criteria it needs. `run_task.py --start` (from `models.worker`) moves the start, and learned floors only matter above it. An effort failure, or any failure below the model's default effort, re-runs on the same model at `high`; a capability failure moves to the next model at its default effort, with Opus going to `xhigh` before Fable. `plan.max_model` caps it. Fable calls carry `--fallback-model opus`, and a call that fell back is not routing evidence. `router.py ladder` prints the ladder and role defaults; `router.py route --type bugfix:api --tier T1` checks one decision.

**The bar.** Briefs number the definition of done: `[D#]` for the task's `done`, `[U#]` for `UNIVERSAL_BAR` plus `plan.quality_bar`. `run_task.py --done-ids` checks the report's `done_check` after verify passes, and any gap is a failed attempt. `raise_bar()` adopts criteria from subagent reports, the manager's `raise_bar` action, reviewers' `raise_bar` and blocking findings. Each goes into a not-started task's `done`, otherwise into `acceptance`; additions are deduplicated and capped. `apply_actions` rejects any change that drops a `done` or `acceptance` criterion. Every addition is logged in `job.json` → `bar`.

Role models live in `scripts/models.py`: advisor Fable 5.2 at medium (asked again at high when medium finds nothing), planner Fable 5.2 at medium, manager, worker, reviewer, area reviewers, UI reviewer, cleanup and integrator Opus 5.5 at medium, failure classifier Haiku 5.5 at low, lessons Haiku at medium. Override per plan with `models`.

The advisor runs at two points. `plan_gate` asks it about `plan.json` before any task starts; a blocker/major finding or a `revise` verdict ends the job as `advisor_blocked` (exit 9), and `--approve advisor:plan` (through the approval hook) overrides it. After a review round passes, `final_gate` runs the cleanup subagent on the integration branch (kept only if it edits just the job's files and verify still passes), then asks the advisor for the final check; its blocking findings go to the manager as `review_changes_requested` with `source: advisor` and become criteria the next round must meet. An advisor with no usable answer fails closed. Its `done_restated` (the definition of done in its own words) is printed in the exit-9 message and in `report.md`: a restatement that misreads done makes its findings suspect. Outside a job, `orchestrate.py advise` runs the same checks for a single task.

Whether the second, high-effort advisor call pays is measured, not assumed. `job_metrics` derives `advisor_calls`, `advisor_escalated` (results from the re-check), `advisor_escalation_found` (re-checks with blocking findings) and `advisor_escalation_cost_usd` from the job state; `report.md` prints them in one line, and each job that ends (or stops at `advisor_blocked`) appends `{job, calls, escalated, found, escalation_cost_usd}` to `advice.jsonl`; `router.py status` keeps the last row per job, so a resumed job counts once, as it ended. Only calls tagged `escalated` when made count as re-check cost (an advisor whose own effort is already high has no re-check) next to `task_costs.jsonl`. `router.py status` adds the rows up (re-checks that found something, of all re-checks, over how many jobs, total cost). It is information only: nothing changes `ADVISOR_ESCALATE`. If the re-check finds nothing over many jobs, the user can lower it in `models.py`. A blocking finding from the re-check isn't proof of value either: it may be a false positive.

`orchestrate.py plan` (the planner subagent) takes the confirmed grill summary as repeatable `--acceptance`, `--decision` and `--non-goal` flags. After every reply, `pin_settled` puts back the user's definition of done, decisions and non-goals verbatim and any user criterion the planner dropped (its extra criteria stay); a decision only the planner wrote moves to `assumptions`, also when the user gave no `--decision` (then `decisions` is empty). `assumptions` holds choices the planner made that nobody confirmed; `validate` warns on each one, `run` refuses a plan that still has any (exit 2, listing them), and no subagent, reviewer or manager prompt sees them.

Separately, `plan.advisor` turns on Claude Code's advisor tool inside each worker (`run_task.py --advisor`). The worker decides when to call it, so the prompt tells it when: before committing to an approach, when an error repeats, and before the final report (on an Anthropic benchmark Opus rarely consulted unprompted and scored 7 points below Opus alone). `max_model` caps the advisor, and an advisor ranked below the worker isn't passed. A launch refused because of the advisor (for example Fable's usage-credits consent) is re-run without it and recorded as `advisor_off`, not as a model failure. Each advisor call re-reads the whole worker session uncached, which is why it stays opt-in.

Each config gets 2 attempts. API overloads and rate limits are retried with backoff first and never count against a model. Then the failure is classified:

| Cause | This task | Future tasks |
|---|---|---|
| environment (services down, a verify command that can't run) | stop | nothing |
| context (missing knowledge) | retry with a hint | proposal: AGENTS.md note |
| effort (cut corners, ran out of turns) | same model, more effort | evidence for a floor raise |
| capability (tried, still wrong) | next model | evidence for a floor raise |

Learning, all as proposals the user approves:
- A floor raise is proposed after ≥2 failed tasks at a config for a type within 30 days, with a failure rate above 50%. Approved floors expire after 30 days or when a new model version ships. About 10% of tasks probe one rung cheaper, so floors can come back down.
- After each job, a cheap extractor reads what the manager, subagents and reviewer wrote and proposes AGENTS.md notes. An approved note goes at the end of the `## Agent notes (learned)` section (before the next `#` or `##` heading; the section is created at the end of the file if missing), and every other byte of the file stays as it was.
- `router.py status` shows the cost per completed task including the coordination it caused.

## Budget

`budget_usd` is passed to every model call as `--max-budget-usd` (the remaining amount), and the scheduler stops launching tasks once it is spent.

## Hermetic calls

`ORCHESTRATE_HERMETIC=1` makes every `claude_cli.call` add `--strict-mcp-config`, `--mcp-config '{"mcpServers":{}}'` and `disableAllHooks` merged into its `--settings` (so `blockWritesOutsideWorkingDirectories` stays), and the user's MCP servers and hooks don't load. CLAUDE.md, rules and other setting sources still load. It is off by default in jobs; `evals/run.py` sets it unless given `--no-hermetic`.

## Finding jobs and checking the install

`status --repo <repo> --open` lists that repo's jobs that are not `done` and not cleaned, newest first, as JSON (`[]` when there are none). Each row has the status (a `running` job whose process is gone shows as `stopped (process gone)`), when job.json last changed, the first line of the message, the manager's question, gated and failed tasks, and the next step from the skill's outcome table. It only reads: it never answers a gate or a question. `clean` stamps `cleaned_at` into job.json, which takes the job off the list; a resume clears it. `status` and `wait` with no job id and `--repo` pick that repo's newest job instead of the newest job of any repo.

`doctor [--repo R]` prints the scripts directory and checks what would otherwise fail late or silently: `claude` must be on PATH (an error, exit 1), and the approval hook should be installed (a warning that prints the hook to add). The hook counts as installed when a `PreToolUse` command naming `approval_gate.py` is in `~/.claude/settings.json`, `~/.claude/settings.local.json` or the repo's `.claude/settings*.json`, or when the orchestrate plugin, which ships it, is enabled there. It makes no model calls.
